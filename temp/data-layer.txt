# Unified Data Layer

A production-grade REST data access layer that provides a consistent interface to heterogeneous data sources, including relational databases, NoSQL databases, legacy systems, and other backend data services.

The platform abstracts source-specific implementation details behind a unified API while providing enterprise-grade security, reliability, observability, governance, and performance controls.

---

## 1. Overview

Organizations often have data distributed across multiple database systems:

```text
PostgreSQL
MySQL
Oracle
MongoDB
Redis
Legacy Systems
External APIs
      |
      v
+-------------------------+
|    Unified Data Layer   |
|                         |
|  Authentication         |
|  Authorization          |
|  Data Modeling          |
|  Query Translation      |
|  Rate Limiting          |
|  Caching                |
|  Observability          |
|  Audit                  |
+-------------------------+
      |
      v
Unified REST APIs
      |
      v
Applications / Services / Analytics / AI
```

The Unified Data Layer provides a single contract for accessing this distributed data without requiring consumers to understand the underlying database technology.

### Goals

* Provide a consistent REST API across heterogeneous data sources.
* Hide backend-specific implementation details.
* Establish a canonical data model.
* Provide centralized authentication and authorization.
* Enforce security, rate limits, quotas, and resource protection.
* Provide consistent pagination, filtering, sorting, and querying.
* Standardize errors and API behavior.
* Provide observability across the complete request path.
* Support reliable reads and writes across distributed systems.
* Provide data lineage, provenance, and auditability.
* Enable independent evolution of source databases and API consumers.

---

# 2. Design Principles

### Backend independence

Consumers should not need to know whether data comes from PostgreSQL, MongoDB, Oracle, or another system.

### Contract first

The REST API and canonical schema are the contracts. Backend schemas are implementation details.

### Secure by default

Authentication, authorization, encryption, validation, auditing, and resource limits are built into the platform rather than delegated to individual consumers.

### Fail explicitly

Unsupported operations, stale data, backend failures, and consistency limitations should be explicit rather than silently producing incorrect results.

### Observable by default

Every request should be traceable across the API, data layer, adapters, and underlying databases.

### Protect the source systems

The unified layer must prevent consumers from accidentally overwhelming legacy or capacity-constrained databases.

## 4.2 Authentication

Supported mechanisms may include:

* OAuth 2.0
* OpenID Connect
* JWT
* API keys
* Service accounts
* Machine-to-machine authentication

Example:

```http
Authorization: Bearer <access_token>
```

Authentication establishes the identity of the caller.

---

## 4.3 Authorization

Authorization determines what an authenticated caller can access.

The platform should support:

* RBAC
* ABAC where required
* OAuth scopes
* Resource-level permissions
* Field-level permissions
* Row-level restrictions
* Tenant-level isolation
* Read/write/delete permissions

Example:

```text
Application A
 └── Customer data
      ├── READ       ✓
      ├── CREATE     ✓
      ├── UPDATE     ✓
      └── DELETE     ✗
```

Authorization must be enforced by the data layer rather than relying solely on consumers.

# 5. Canonical Data Model

The platform exposes a canonical representation of data.

For example, three source systems may represent a customer differently:

```text
PostgreSQL:
customer_id
first_name
last_name

MongoDB:
_id
name
surname

Oracle:
CUST_NO
FNAME
LNAME
```

The Unified Data Layer exposes:

```json
{
  "id": "123",
  "firstName": "John",
  "lastName": "Smith"
}
```

The canonical model defines:

* Entity names
* Field names
* Data types
* Relationships
* Enumerations
* Required fields
* Optional fields
* Units
* Identity mappings
* Source mappings

# 6. Data Source Adapters

Each backend is accessed through an adapter.

```text
Unified Data Layer
        |
        +-- PostgreSQL Adapter
        |
        +-- MySQL Adapter
        |
        +-- MongoDB Adapter
        |
        +-- Oracle Adapter
        |
        +-- External API Adapter
```

An adapter is responsible for:

* Connection management
* Authentication to the source
* Query translation
* Data-type conversion
* Pagination translation
* Error translation
* Transaction handling
* Backend-specific capabilities
* Connection pooling

Backend-specific logic should not leak into the public API.

# 7. REST API

All resources should follow consistent REST conventions.

Example:

```http
GET    /v1/customers
GET    /v1/customers/{id}
POST   /v1/customers
PATCH  /v1/customers/{id}
DELETE /v1/customers/{id}
```

---

# 8. API Versioning

APIs are versioned explicitly.

```text
/v1/customers
/v2/customers
```

The platform should define:

* Breaking-change policy
* Backward compatibility requirements
* Deprecation periods
* Migration procedures
* Sunset policy

Non-breaking changes should preferably be introduced without creating a new version.

---

# 9. Pagination

Large collections must always be paginated.

Cursor pagination is preferred:

```http
GET /v1/customers?limit=100&cursor=<cursor>
```

Response:

```json
{
  "data": [],
  "pagination": {
    "nextCursor": "<cursor>",
    "hasMore": true
  }
}
```

Requirements:

* Maximum page size
* Default page size
* Stable ordering
* Cursor validation
* Cursor expiration where appropriate
* Consistent pagination semantics

---

# 10. Filtering

Resources should support controlled filtering.

Example:

```http
GET /v1/customers?status=active&country=IN
```

Range filtering:

```http
GET /v1/orders?createdAt[gte]=2026-01-01
```

Filtering capabilities must be validated and translated by the adapter layer.

Arbitrary SQL execution must not be exposed through the public API.

---

# 11. Sorting

Example:

```http
GET /v1/customers?sort=-createdAt
```

Multiple fields:

```http
GET /v1/customers?sort=-createdAt,name
```

Only explicitly supported fields should be sortable.

---

# 12. Field Selection

Clients should be able to request only required fields.

```http
GET /v1/customers/123?fields=id,name,email
```

This reduces:

* Network traffic
* Serialization cost
* Database work
* Response latency

Sensitive fields must remain subject to authorization regardless of field selection.

---

# 13. Standard Error Model

All APIs should return a consistent error structure.

Example:

```json
{
  "error": {
    "code": "CUSTOMER_NOT_FOUND",
    "message": "Customer does not exist.",
    "requestId": "req_123456",
    "details": {}
  }
}
```

Common HTTP status codes:

| Status | Meaning             |
| ------ | ------------------- |
| `400`  | Invalid request     |
| `401`  | Unauthenticated     |
| `403`  | Unauthorized        |
| `404`  | Resource not found  |
| `409`  | Conflict            |
| `422`  | Validation failure  |
| `429`  | Rate limit exceeded |
| `500`  | Internal error      |
| `502`  | Backend failure     |
| `503`  | Service unavailable |
| `504`  | Backend timeout     |

Raw database errors must never be exposed to consumers.

# 14. Rate Limiting

Rate limits should be enforceable at multiple levels:

```text
IP
User
API Key
Service
Tenant
Endpoint
```

Example:

```text
1000 requests/minute per API key
10,000 requests/minute per tenant
```

When exceeded:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
```

Rate limiting should be complemented by concurrency limits and query-cost controls.

# 15. Quotas

Quotas control longer-term resource consumption.

Possible dimensions:

* Requests/day
* Requests/month
* Data volume
* Export volume
* Concurrent requests
* Expensive query execution
* Storage
* Async jobs

# 16. Query Protection

The platform must protect source databases from expensive requests.

Controls include:

* Query timeout
* Maximum result size
* Maximum page size
* Maximum query complexity
* Maximum joins
* Maximum concurrent queries
* Maximum export size
* Backend-specific query limits

Example:

```text
Client
  |
  | expensive query
  v
Unified Layer
  |
  +-- Query validation
  +-- Cost estimation
  +-- Authorization
  +-- Resource limits
  |
  v

```

# 17. Timeouts

Every request and backend operation should have explicit timeouts.

Example:

```text
API timeout:             5 seconds
Database query timeout:  3 seconds
Connection timeout:      1 second
```

Timeout values should be configurable by operation and backend where necessary.

---

# 18. Retries

Retries should be carefully controlled.

Safe candidates generally include:

* Idempotent reads
* Transient network failures
* Temporary backend unavailability

Retries should use:

* Exponential backoff
* Jitter
* Maximum retry count
* Retryable-error classification

Non-idempotent writes must not be blindly retried.

---

# 19. Idempotency

Write operations should support idempotency where duplicate execution would be harmful.

Example:

```http
POST /v1/orders

Idempotency-Key: 8f7e2c1a
```

Repeated requests using the same idempotency key should produce the same logical operation rather than creating duplicate records.

---

# 20. Concurrency Control

The platform should support optimistic concurrency.

Example:

```http
If-Match: "version-42"
```

If another client has modified the resource:

```http
409 Conflict
```

or an appropriate precondition status can be returned.

This prevents lost updates.

---

# 21. Consistency

The platform must explicitly document consistency guarantees.

Possible models:

* Strong consistency
* Eventual consistency
* Read-after-write consistency
* Source-dependent consistency

Example:

```text
Customer database
      |
      | update
      v
Unified API
      |
      +--> Customer DB
      |
      +--> Search index
```

The API must make it clear when the search index may temporarily lag behind the source database.

---

# 22. Distributed Writes

When a single operation modifies multiple databases, distributed transaction behavior must be explicitly defined.

Possible approaches:

* Database transaction
* Two-phase commit where appropriate
* Saga
* Outbox pattern
* Event-driven processing
* Compensation
* Retry and reconciliation

Example:

```text
API
 |
 +--> DB A
 |      |
 |    Outbox
 |      |
 |    Event
 |      |
 +--> Queue
        |
        +--> DB B
```

---

# 23. Bulk Operations

Bulk APIs should be supported for high-volume operations.

Example:

```http
POST /v1/customers/bulk
```

Bulk operations require:

* Maximum batch size
* Validation
* Partial failure handling
* Per-record errors
* Idempotency
* Async processing for large jobs

---

# 24. Asynchronous Operations

Long-running operations should not block HTTP requests.

Example:

```http
POST /v1/exports
```

Response:

```json
{
  "jobId": "job_123",
  "status": "pending"
}
```

Then:

```http
GET /v1/jobs/job_123
```

Suitable for:

* Large exports
* Bulk updates
* Data synchronization
* Backfills
* Large reports
* Data migrations

# 30. Data Freshness

When multiple sources have different update frequencies, freshness should be measurable.

Example:

```json
{
  "_metadata": {
    "sourceUpdatedAt": "2026-08-17T03:00:00Z",
    "retrievedAt": "2026-08-17T03:01:00Z"
  }
}
```

This allows consumers to distinguish real-time data from replicated or cached data.

# 33. Health Checks

```http

```

Determines whether the service process is functioning.

### Readiness

Determines whether the service can accept traffic.

Dependency health can be exposed internally:

```text

Oracle         DEGRADED
```

# 35. Circuit Breakers

If a backend becomes unhealthy:

```text
Unified API
     |
     v
Oracle Adapter
     |
     X
Oracle unavailable
```

The adapter should eventually open its circuit and fail fast rather than continuously generating additional load.

States:

```text
CLOSED
   |
   v
OPEN
   |
   v
HALF-OPEN
   |
   v
CLOSED
```

| Filtering         |        Yes |     Yes |       Yes |
| Sorting           |        Yes |     Yes |       Yes |

| Aggregation       |        Yes |     Yes |   Depends |

* [ ] All collection endpoints support bounded pagination.

* [ ] Query complexity and resource usage are bounded.
* [ ] Rate limits and quotas are enforced.
* [ ] Requests have timeouts.
* [ ] Retry behavior is explicitly defined.
* [ ] Non-idempotent operations have appropriate idempotency controls.

* [ ] All requests have correlation IDs.
* [ ] Metrics and distributed tracing are available.
* [ ] Sensitive operations are audited.

It should provide a **stable, secure, observable, governed abstraction over heterogeneous data sources**.

```text
        +-------------------+-------------------+
                            |
                     Unified REST API
                            |
                 Canonical Data Model
                            |
                   Query / Command Layer
                            |
                     Adapter Framework
                            |
             +--------------+--------------+
             |              |              |
          Database A     Database B     Database C
```

The central architectural principle is:

> **Consumers interact with a stable canonical API; adapters translate that contract into the capabilities and semantics of each underlying data source.**

This separation allows databases to change independently while keeping downstream applications insulated from backend-specific complexity.
